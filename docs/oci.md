# OCI reference deployment

The implemented first stage is a private **Compute + managed PostgreSQL 17** cell. `infra/oci-reference` is an OCI Resource Manager uploadable Terraform stack. `infra/oci-evidence` is a separate retained bucket stack. The reference cell was first applied from local Terraform in Phoenix on 12 October 2026, using an existing private, versioned evidence bucket created separately. All four VM bootstraps completed, PostgreSQL 17.6 became ACTIVE, and the OCI Bastion tunnel was verified. A post-apply plan reported no changes. Application deployment and PostgreSQL-backed golden/smoke checks completed on 13 October; performance validation remains incomplete (retained in the private research archive).

## 1. Resolve placement, access and cost before provisioning

Supply the region, isolated existing compartment OCID, full availability-domain name, a region-specific Ubuntu 24.04 x86_64 image OCID, SSH **public** key, campaign USD ceiling and a retained evidence bucket name. Use the PostgreSQL ListShapes `id`, such as `PostgreSQL.VM.Standard.E5.Flex`, for `db_shape`; its `shape` field is the underlying Compute name and is not accepted by CreateDbSystem. Select OCPUs and memory within that service shape's returned limits, and a supported IOPS tier. A Compute E5 shape being available does not prove the same PostgreSQL shape or quota is available.

The four default VM roles are separate: controller/build runner 2 OCPU/16 GB, Fluxnova 2 OCPU/16 GB, generator 2 OCPU/8 GB and support/telemetry 2 OCPU/8 GB, all `VM.Standard.E5.Flex`. On these x86 machines 2 OCPU means 4 logical vCPUs. The app container has its own pinned 4-CPU/8-GiB/4-GiB-heap budget in the run configuration. These are starting configurations, not performance claims. Add the managed database, four boot volumes, NAT, storage, telemetry and registry charges to the estimate; the controller is not free while idle.

`budget_limit_usd` is a required recorded ceiling **and does not enforce a hard billing cap**. Create compartment budget actual/forecast alerts using OCI Billing before apply and record the expected campaign end time. The root CLI bounds load-run duration; it does not implement an automatic resource-expiry service. The operator must archive evidence and run teardown at the agreed expiry. Stopping a load generator does not stop database or infrastructure charges.

All VM VNICs are private. Set `bastion_client_cidrs` to your workstation's public IPv4 `/32` to enable OCI Bastion. Terraform adds a separate private endpoint subnet, permits its egress only to the controller's private IP on TCP/22, and admits only the Bastion endpoint `/32` into the controller's NSG. With the default VCN `10.78.0.0/16`, compute uses `10.78.0.0/24`, PostgreSQL uses `10.78.1.0/24`, and the optional Bastion endpoint uses `10.78.2.0/24`. The VCN has NAT for outbound package downloads and a service gateway for OCI services; it has no internet gateway or public VM addresses.

Alternatively, use an existing routed VPN/DRG path and add its private source CIDR to `administrator_cidrs`. Both access lists default to empty. Adding an administrator CIDR creates a security rule, not a route. Resource Manager itself does not need SSH access. The initial plan/apply must run from an authorized workstation, Cloud Shell or administrative runner because the new controller does not exist yet. After bootstrap, its OCI SDK authentication method is `instance_principal`.

### Forward controller SSH through OCI Bastion

After applying the reviewed plan, run from the repository root on your workstation:

```powershell
python -m pip install oci==2.187.1
oci session authenticate --profile-name BENCHMARK --region us-phoenix-1
python scripts/bastion_forward.py
```

Skip authentication if the session is still valid. The script defaults to `~/.ssh/fluxnova_bench`, public key `~/.ssh/fluxnova_bench.pub`, profile `BENCHMARK`, and local port `2222`. It reads `terraform output -json environment_contract` from `infra/oci-reference`. For Resource Manager, export its applied `environment_contract` as UTF-8 JSON and pass `--contract environment.local.json`; the script also accepts the full `terraform output -json` wrapper. Run `--help` for path, profile, port, and TTL options. A plan alone has no deployed Bastion or controller address.

On the workstation used for the first deployment, the OCI CLI's Python environment already contains the SDK. Reuse it without another package installation:

```powershell
& "$env:USERPROFILE\oci\Scripts\python.exe" .\scripts\bastion_forward.py
```

The script creates a 30-minute SSH port-forwarding session, waits for ACTIVE, and starts OpenSSH bound only to `127.0.0.1`. Follow the normal SSH host-key prompt. A newly ACTIVE session can initially reject SSH authentication, as observed during this deployment. The script retries startup SSH failures (exit 255) using the same session, up to six attempts spaced ten seconds apart within a 120-second startup window. It prints `Ready: controller SSH responded` only after receiving the controller's SSH banner through the tunnel. Wait for that message before using the printed SSH command in a second terminal to connect as `ubuntu`; a local listener alone does not prove the controller is reachable.

Keep the first terminal open. Ctrl+C stops the local tunnel and requests deletion of that session; server-side expiry still applies if deletion fails. Rerun to get a new session. An established tunnel that later exits is not automatically recreated. If all startup retries fail, inspect the SSH error, matching private/public key files, client IP allowlist and session TTL. A second connection reporting `Connection refused` on port 2222 means the first tunnel is unavailable; restore it first. See Oracle's [Bastion connection troubleshooting](https://docs.oracle.com/en-us/iaas/Content/Bastion/Tasks/troubleshooting_connect_session_failed.htm) for persistent errors. This port-forwarding mode needs no Bastion agent on the VM and does not forward your SSH agent. The private key stays on your workstation.

To reach the app after it is deployed, add `-L 127.0.0.1:8080:APP_PRIVATE_IP:8080` to the printed controller SSH command, using the `roles.app.private_ip` from the applied contract. This second SSH connection forwards app traffic through the controller's existing permitted route. Then open `http://127.0.0.1:8080/engine-rest` locally.

If your public IP changes (including VPN changes), update `bastion_client_cidrs`, review and apply that change, then reconnect. The deployment principal needs Bastion and network management permissions; the session operator needs access to the intended Bastion and permission to create/read/delete its sessions. See Oracle's [Bastion IAM policies](https://docs.oracle.com/en-us/iaas/Content/Bastion/Reference/bastionpolicyreference.htm) and [port-forwarding instructions](https://docs.oracle.com/en-us/iaas/Content/Bastion/Tasks/connect-port-forwarding.htm). For benchmark CLI provisioning, put the list under `oci.terraform_variables.bastion_client_cidrs` in the JSON configuration; the CLI does not read local tfvars.

## 2. Prepare IAM and Vault references

The stack deliberately does not edit tenancy-wide identity policies or create administrator passwords. Have an OCI administrator configure these narrowly for the dedicated compartment and reviewed resource identities:

- Resource Manager's stack resource principal needs the ability to manage the VCN, subnets, NSGs, routes/gateways, instances/boot volumes, PostgreSQL DB system and private container repository in the benchmark compartment, plus read the retained bucket and namespace. Grant PostgreSQL service access to the selected Vault secret/key according to OCI's database/Vault setup guidance. Use a Resource Manager dynamic group restricted to the intended stack OCID or benchmark compartment; never a tenancy-wide wildcard merely for convenience.
- The controller instance dynamic group needs read access to the chosen secret bundle, PostgreSQL connection details and instance metadata, read/write benchmark object operations in the named evidence bucket, and the specifically chosen Resource Manager stack operations. Registry push uses an OCI auth token; do not assume an instance principal can run `docker login` without registry credentials.
- Application hosts need only the runtime secrets and image pull path their deployment method uses. Do not grant the load generator infrastructure management rights. If the controller reads the DB secret and creates a protected runtime environment file remotely, do not distribute the admin secret to the generator.
- Store the database administrator password in an existing OCI Vault secret and supply `db_admin_secret_id` plus a fixed `db_admin_secret_version` (default 1). Terraform sends the secret reference directly using the `VAULT_SECRET` password type. It does not read or output the password. The initial isolated reference profile uses this administrator for schema bootstrap/runtime unless `runtime.db_user` and `runtime.db_password_secret_id` select a separately provisioned application principal. Record that boundary; use the application principal before treating the configuration as production representative.

IAM policy resource families and conditions must match the organization's identity domains and network controls. Validate the plan under the intended principal. A syntactically valid Terraform plan cannot prove a future VM's dynamic-group membership or database-service permission.

## 3. Create retained evidence, then the reference cell

**Existing local deployment (12 October 2026):** the reference cell has already been applied; do not create another Resource Manager stack to continue it. Its state is `infra/oci-reference/terraform.tfstate`, which must be protected and backed up. The applied contract and no-change verification plan are saved under the ignored `dist/oci-plan-20261012-bastion/` directory as `environment.local.json` and `verification-plan.txt`. The existing `infra` bucket was created separately and versioning was verified; `infra/oci-evidence` was not applied, so its Terraform deletion protection does not manage this bucket. Continue with [application preparation](#4-resolve-database-tls-and-deploy-the-application) and the [campaign resume checklist](campaign-runbook.md#resume-the-existing-local-deployment).

For a new Resource Manager deployment:

1. Zip the **contents** of `infra/oci-evidence` and upload them as their own Resource Manager stack. Set `region`, `compartment_id`, `artifact_bucket_name`. Review the plan and apply. Save its stack ID separately. The bucket is private and versioned, with Terraform deletion protection and no automatic object expiry.
2. Set the same `artifact_bucket_name` in the root campaign's OCI configuration. The ephemeral stack discovers the namespace itself; there is no required `artifact_namespace` or registry-host variable. Use the CLI `package`/`provision` commands described in the root README. Root CLI provisioning operates on `oci-reference`, not the evidence stack.
3. Review the Resource Manager plan for the four expected VMs, one PostgreSQL instance, two private subnets, one VCN, NAT/service gateways, NSGs and the private container repository. OCI rejected the `isImmutable` creation property during Phoenix bring-up; the stack omits it, and runtime image references must remain pinned by digest. Enabling Bastion adds the service, a third private subnet, its security list and one controller ingress rule. The retained bucket appears only as a data read. Apply the reviewed plan through the root CLI when campaign inputs are complete.
4. Export the non-secret `environment_contract`. It contains role private IPs/users/resources, database identity and secret reference, artifact namespace/bucket, and OCIR host/namespace/repository. The contract is inventory, not a successful application-health assertion.
5. Wait for `cloud-init status --wait` on every host and check `/opt/fluxnova-bench/bootstrap-complete`. Verify Python >=3.12, Docker daemon availability and the installed-version receipts. Upload the reviewed project archive to `/opt/fluxnova-bench/workspace`, install pinned `requirements-cloud.txt` into `/opt/fluxnova-bench/venv`, and install the project there. Run `python -m benchlib.cli` from the workspace using that venv.

The image OCID is pinned. `package_versions` accepts exact Debian versions for `python3`, `python3-venv`, `docker.io`, `docker-compose-v2` and `git`; with an empty map bootstrap resolves the image's repositories and records versions. This mode is suitable for bring-up, not an assertion of byte-identical rebuilds. Before comparisons, supply exact available package versions or freeze a tested custom image and its provenance. Package version lookup and application installation are not hidden in Terraform remote-exec provisioners.

The NSGs permit the controller to SSH to the other roles; controller/loadgen/support may reach the app API; app/controller/loadgen may reach support; only app/controller reach PostgreSQL. DNS/NTP, necessary link-local metadata, bootstrap HTTP/HTTPS, and path-MTU ICMP are supported. Package egress uses NAT; OCI-service traffic uses the service gateway. There is no public application ingress, load balancer, or automatic DRG provisioning. Optional OCI Bastion exposes only controller SSH through temporary sessions. Private plain HTTP between benchmark hosts is explicit in the contract; use the CLI's private-HTTP setting knowingly or supply TLS termination for a separate security profile.

## 4. Resolve database TLS and deploy the application

For the first local deployment, infrastructure, registry authentication, image publication and private application deployment are complete. As of 13 October, database checks pass with verified TLS and the dedicated application principal; golden checks and follow-up telemetry/load tests pass. A controlled baseline and actual cost evidence remain outstanding. The workstation's private Bastion key stays on the workstation. See the [prepared-controller details](remote-deployment.md#continue-the-prepared-phoenix-controller), [web UI access](web-ui.md), and latest validation (retained in the private research archive).

Post-apply, call `PostgresqlClient.get_connection_details(db_system_id)` through the pinned OCI SDK. Save the returned service CA certificate in a protected local file and use `primary_db_endpoint.fqdn`/`port` for JDBC with `sslmode=verify-full`. The initial Terraform database `host` is the private IP for inventory; do not blindly use it as the TLS server name. Never solve a hostname/CA mismatch by disabling certificate validation.

Run schema creation with the Fluxnova release's actual PostgreSQL scripts and then use an application principal for runtime. Confirm the actual database version, READ_COMMITTED isolation, schema version and tested JDBC driver in the manifest. Execute basic start/end, persistent/transient-variable, asynchronous completion and retry tests before starting throughput tests. Discover the application artifacts from the reviewed build path; published GitHub releases do not guarantee a corresponding Docker tag exists. Release 3.0.1 is a published release, but registry availability must be checked independently and a source/Maven-distribution build pinned by checksum is a supported preparation path.

Run remote deployment from the private controller with its configured SSH identity; use the root CLI to deploy the app, support/worker and isolated load generator. Archive cloud-init/version receipts, deployment hashes, image digests, run configuration and the final environment contract with each campaign.

## 5. Teardown and later comparison lanes

After raw events, telemetry, normalized results and reports have been uploaded and their checksums verified, destroy only the reference cell using the tool that owns its state. For the existing local deployment, review a local Terraform destroy plan in `infra/oci-reference` and apply that reviewed plan. For a Resource Manager deployment, use the root CLI's saved-stack teardown. This removes the ephemeral compute/database/network/repository resources. The evidence bucket remains outside the reference state, either managed separately or by the evidence stack. Database backups can outlive DB deletion according to OCI policy and should be included in the final cost/retention inventory. Deleting the evidence bucket requires an explicit archival/retention decision; do not remove it during routine cell teardown.

OKE, Autonomous Database and live agentic lanes remain **planned extensions**, not implemented Terraform profiles in this release. Add them only after this cell passes compatibility and measurement validation. An OKE comparison must preserve artifact digest, logical CPU/memory/JVM, PostgreSQL data/history, generator and network boundary; fix replicas before testing autoscaling. Oracle 19c/23ai compatibility needs independent service validation. A console 26ai label cannot prove the actual engine is within Fluxnova's support matrix. Preserve released 3.0.1 and development-SHA lanes separately.

## Local checks and limitations

Validation on 29 September 2026: both stacks passed `terraform validate` with Terraform 1.13.5 and the pinned Oracle OCI provider 7.22.0. The reference stack's two mocked tests passed, covering private topology/Vault references and rejection of unrestricted administrative ingress. These checks created no cloud resources. The provider lock files are retained in both stack directories. The HCL uses Terraform 1.5-compatible configuration features; mocked local tests require Terraform 1.7 or newer and are not run during Resource Manager plan/apply. Select an available Resource Manager Terraform version when creating the stack rather than assuming the local validation binary is available there.

Validation on 12 October 2026: five reference-stack mocked tests and all 99 Python unit tests (including eight Bastion forwarding tests) passed. The local deployment completed with 73 resources and a subsequent no-change plan. All four hosts completed cloud-init; controller Python 3.12.3, Docker 29.1.3 and Compose 2.40.3 were verified. The project and cloud/database dependencies were installed on the controller. PostgreSQL reported 17.6 ACTIVE, verified TLS 1.3 and hostname checks passed, and login using the pinned Vault secret succeeded with read committed isolation. No schema changes were made. Fluxnova deployment, golden workflows, telemetry and performance remain unverified.

Run `scripts/infra-validate.ps1` (or `terraform fmt -check`, `terraform init -backend=false`, `terraform validate` separately in both stack directories). No credentials or apply are needed for provider schema validation. `terraform init` downloads the pinned `oracle/oci` 7.22.0 provider and creates the lock file; retain its hashes in review. Resource Manager still needs its own successful plan against the real region, shape, image and IAM. A successful local deployment establishes capacity only for the resources created at that time, not future quota or capacity availability.
