## Version and REST compatibility

All payload sizes use the Fluxnova `Bytes` variable type, base64 on REST input, to compare the same persistence representation at 1/32/256KiB. The supplied small transient string and persistent Boolean remain unchanged. Initial real-engine tests correctly exposed the database string-column limit when 32/256KiB was sent as `String`; those failed observations must be retained. Payload assertions fetch `/history/variable-instance/{id}/data` and compare the actual bytes, rather than treating a null inline value as missing or correct. Base64 encoding and blob retrieval costs are included and must remain consistent between systems.

For 3.0.1, these BPMNs use `http://camunda.org/schema/1.0/bpmn` for history TTL, async and external-task attributes. The published model API also declares a Fluxnova namespace, but the released engine's parser still reads the older namespace for these attributes. A deployment test found that using the Fluxnova namespace here caused TTL validation failure. Keep this version-specific compatibility choice until a new engine build passes deployment and functional checks. History TTL is 30 days; the tested engine history level must be `full` for the assertions below. Do not silently change history level between comparisons.

Primary source: [BpmnParse at v3.0.1](https://github.com/finos/fluxnova-bpm-platform/blob/v3.0.1/engine/src/main/java/org/finos/fluxnova/bpm/engine/impl/bpmn/parser/BpmnParse.java), [model namespaces](https://github.com/finos/fluxnova-bpm-platform/blob/v3.0.1/model-api/bpmn-model/src/main/java/org/finos/fluxnova/bpm/model/bpmn/impl/BpmnModelConstants.java).

REST paths are relative to the configured engine root, normally `/engine-rest`: `POST /deployment/create`, `POST /process-definition/key/{key}/start`, `POST /external-task/fetchAndLock`, `POST /external-task/{id}/complete`, `POST /external-task/{id}/failure`, `GET /history/process-instance/{id}`, `GET /history/variable-instance?processInstanceId=...`, and `GET /history/activity-instance?processInstanceId=...`. KYC goldens also query `/task` and complete `/task/{id}/complete`. The local functional checks use those actual endpoints; they do not prove managed PostgreSQL or Oracle compatibility.

## Start support and workers

```text
python -m services.mock_service --host 127.0.0.1 --port 18081 --database runs/support.sqlite
python -m services.worker --engine-url http://127.0.0.1:18080/engine-rest --support-url http://127.0.0.1:18081
python -m services.golden --engine-url http://127.0.0.1:18080/engine-rest --support-url http://127.0.0.1:18081 --output-dir runs/golden-001
```

Deploy all six BPMNs first. Engine Basic authentication uses `BENCH_USERNAME`/`BENCH_PASSWORD`; support bearer authentication uses `BENCH_SUPPORT_TOKEN`. Set the support token whenever binding beyond loopback. Docker defaults are `BENCH_BIND=0.0.0.0`, `BENCH_PORT=8090`, `BENCH_DB=/data/support.sqlite`; mount a persistent writable `/data`. The image runs as UID65532. Use `python -m services.worker` as the image command for workers. Each worker fetches one external task with a 60-second lock and makes bounded 10-second HTTP calls; scale the worker replicas separately and record their resources to avoid confusing worker saturation with engine capacity.

The worker continues immediately after successful completion. `--poll-s` (default 0.1 seconds) controls backoff after an empty poll, task failure or polling transport error. It does not delay each successful task. One-task locking, bounded retries and simulator reconciliation remain unchanged. Record the worker image separately when testing worker changes: optional `artifact.worker_image` overrides the worker's image, while `artifact.services_image` continues to identify the simulator image. Both must be immutable digest references; omitting the override uses the shared services image for both roles.

Opt-in worker diagnostics use `--timing`, `BENCH_WORKER_TIMING=1`, or `runtime.worker_timing_enabled: true` when deploying. They emit `worker_poll_timing` for fetch calls and `worker_task_timing` for each task attempt, identifying tool execution, reconciliation, engine completion and failure-reporting calls. Each stage records a UTC start and monotonic duration for the entire client call, including response reading/decoding; it does not isolate server commit, network or scheduling time. Task records carry engine task/process IDs and completion status, without payloads, credentials, business keys or exception messages. Timing records are emitted after calls/attempts finish, so a killed or still-blocked attempt may have no record. Missing records must not be interpreted as fast calls. Diagnostic output failures do not trigger a retry of an already completed task.

Timing is disabled by default. Enabling it adds clock reads and synchronous JSON output, including empty fetches; record this setting and the worker digest in the manifest and treat measured runs as a separate diagnostic configuration. Preserve Docker logs before replacing a worker or restoring state. Use engine process IDs to join task timings to load events, and retain all attempts rather than overwriting retries.

`POST /tools/execute` accepts `idempotency_key`, `operation` (`echo`, `kyc`, `risk`, `settle`), a typed JSON `payload`, optional `delay_ms` 0Ã¢â‚¬â€œ5000, and `fault` (`none`, `before_effect_once`, `after_effect_once`). `GET /state/{key}` independently exposes the committed result, request fingerprint, effect count and policy/audit events. Idempotency is atomic in SQLite, survives restart, and rejects key reuse with another payload using HTTP409. The original request fingerprint is checked before a worker accepts reconciliation. Policy enforcement happens in the simulator before a ledger effect. A repeated business key can still create multiple Fluxnova process instances; only the simulator business effect is deduplicated.

SQLite models the independent tool ledger and is not a candidate engine database. Its throughput is a dependency constraint to measure. It is suitable for functional and controlled mock tests; replace it with an equivalently specified, independently validated backend before making high-scale payment-capacity claims.

## Load, timing and results

`load/benchmark.js` uses k6 constant arrival rate. Each VU starts a workflow and polls durable history plus variables and independent tool state. Schedule timestamps are derived from the scenario's constant-rate plan; actual elapsed time uses k6's monotonic test clock. `BENCH_EVENT` NDJSON lines carry the root event contract and a warmup/measurement phase. Warmup work can drain into measurement; the run reports that overlap. The full wall-time budget is warmup + measurement + drain. Missing observations remain unknown.

Start acknowledgement latency and workflow completion latency are different metrics. Workflow latency ends at the first durable history observation and includes scheduling lag and polling delay. Subsequent variable/blob/ledger validation determines correctness but is excluded from the completion interval; each event retains the observation timestamp, `validation_elapsed_s`, and `verified_at`. Missing oracle evidence remains unknown. This is an externally observed completion upper bound, not an inferred engine-only commit duration. The observer adds API/database load; preserve its interval across comparisons and use traces for internal timing attribution. Raw durations are seconds. Per-request console evidence also consumes generator resources and must be included in generator calibration.

`handleSummary` writes `k6-summary.json`. Its `measurement` section contains planned scheduled count, started count, and the scenario-specific dropped-iteration count. It never declares the generator valid or telemetry complete by itself. Preserve invalid runs. Count every attempted logical request, including errors/unknowns; only correct outcomes meeting the declared deadline count toward goodput. K6 load requires sufficient VUs for the full completion interval, not just start HTTP latency.

Required environment names: `BENCH_BASE_URL`, `BENCH_SUPPORT_URL`, `BENCH_RUN_ID`, `BENCH_SCENARIO`, `BENCH_RATE`, `BENCH_DURATION_S`, `BENCH_WARMUP_S`, `BENCH_DRAIN_S`, `BENCH_DEADLINE_S`, `BENCH_PAYLOAD_BYTES`, `BENCH_PREALLOCATED_VUS`, `BENCH_MAX_VUS`, `BENCH_POLL_INTERVAL_MS`, `BENCH_OUTPUT_DIR`. The deterministic branch pattern alternates by global scenario iteration; `BENCH_SEED` is reserved for later stochastic datasets and is not used to imply random coverage.

## Experimental polling for already-late work

`workload.late_poll_interval_ms` optionally slows completion-history polling after an arrival's declared deadline has already passed. It defaults to `poll_interval_ms`, preserving the previous policy. For example, `poll_interval_ms: 100`, `late_poll_interval_ms: 1000`, `deadline_s: 2`, and `drain_s: 30` retain 100 ms observations before the two-second deadline and use one-second intervals afterward. Sleeps are capped at the remaining observation budget; an HTTP call already in flight retains its own timeout.

The configured interval must be positive, at least the ordinary polling interval, and no longer than the observation budget. Both intervals appear in the raw k6 policy summary and completion-event details. Slower polling does not convert a late completion into a deadline success. The history observation, deadline and subsequent outcome-oracle rules are unchanged.

This candidate addresses load amplification when many unfinished workflows are polled rapidly. Six real k6 fixture checks cover default behavior, warmup aborts, reduced requests for already-late unknown work and unchanged predeadline observation. It has not yet established a live application improvement. Any comparison must pin the same policy in both settings and use a separately named protocol; previous baselines and failed series remain unchanged. The reproduced startup failure (retained in the private research archive) motivates the bounded recovery test.
